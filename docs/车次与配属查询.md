## 1. 车次查询

### 1.1 数据源

| 优先 | 来源 | 能拿到什么 | 说明 |
|---|---|---|---|
| 首选 | **RailGo** `https://data.railgo.zenglingkun.cn/api/train/query?train=G7` | 列车等级、担当局、客运段、**配属段**、车型、时刻表、开行日、交路 | 零鉴权、`Access-Control-Allow-Origin: *`；个人托管服务，可用性无保证 |
| 兜底 | **12306** `search.12306.cn` → `kyfw.12306.cn` | 时刻表（官方口径）、列车等级 | 官方接口，稳定；无担当/配属信息 |

`trainQuerySource` 配置项：`auto`（默认，先 RailGo 失败退 12306）/ `railgo` / `12306`。

### 1.2 统一结果结构（两端一致）

```
ok              bool    查询是否成功
source          str     'railgo' | '12306'
error           str     失败原因（中文，可直接显示）
train           str     车次号（规整为大写）
numberFull      [str]   复车次（如 G100/G97）
category        str     列车等级（高速/动车/新空调快速…）
bureau          str     担当局（京局/上局/…）
runner          str     担当客运段
carOwner        str     配属段（动车所/车辆段）
car             str     车型（CR400AF-BS / 25T…）
rundays         [str]   开行日（YYYYMMDD，91 天）
rundaysCount    int     开行日数量
diagramType     str     直通/管内
diagram         [{number, fromStation, fromTime, toStation, toTime}]   交路
stops           [{no, station, telecode, arrive, depart, stop, day, distance, speed}]
start/end       str     始发/终到站
startTime/endTime str   始发/终到时刻
distance        float   全程里程（km，拿不到为 None）
queryDate       str     12306 查询所用日期
```

### 1.3 实现要点

- 全部走标准库 `urllib`（桌面端不新增依赖），UA 固定为项目标识，10s 超时；
- **任何失败都不抛异常**，返回 `ok=False` + 中文原因（网络不可达 / HTTP 500 / 非 JSON / 未查询到车次）；
- 车次号先规整（去空格、全角转半角、字母大写），再校验 `^[A-Za-z]{0,2}\d{1,5}$`；
- 12306 两段请求：先按日期搜 `train_no`，再查时刻表；停站分钟数由到发时刻相减（跨日不臆测，记 0）；
- RailGo 的 `timetable[].distance` 可能是 `"-"`，要容错成 `None`；
- 频率：**用户手动查询才发请求**，不做预取/轮询；失败的自动重试最多一次（换源），不要循环打。

### 1.4 界面上展示什么

桌面「工具 → 车次查询…」（`Ctrl+F`）/ 「工具 → 机车配属查询…」（`Ctrl+G`）；
安卓「设置 → 查询·数据」子页。

- 顶部：车次大字 + 等级 + 始发→终到 + 始发/终到时刻；
- 信息网格：担当局、客运段、配属段、车型、开行日（数量 + 最近一日）、数据来源；
- 交路（有则列出，无则隐藏）；
- 时刻表（站名 / 到点 / 发点 / 停站 / 里程），里程 `—` 表示源未给；
- 失败时：原因 + 「改用 12306 重试」。

## 2. 机车配属查询

### 2.1 从报文到配属

```
LBJ 长报文 ──► 8 位机车号 = [3 位类型码][1 位][4 位序号]，例：240 0 0123
                    │                    │
                    │                    └─► 序号 123（去前导零）
                    └─► 类型码 240 ──loco_types.csv──► 短型号 HXD1D / 显示名「HXD1D」
                                                        │
                     短型号 + 序号 ──loco_roster.csv──► 配属单位 / 制造厂
```

解码器输出的 `loco` 形如 `HXD1D-0123`（历史车型是中文名，如 `韶山4-0123`），
`locoCode` 是报文里的 3 位类型码。查询时：

1. 优先用 `locoCode` 查 `loco_types.csv` 得到短型号（最可靠）；
2. 没有代号就从 `loco` 文本里拆型号，再用「名称/短型号 → 短型号」归一；
3. 号码取数字部分（去前导零）；
4. 在 `loco_roster.csv` 里按 **型号精确相等 + 起号 ≤ 号 ≤ 止号（闭区间）** 取**第一条**命中。

### 2.2 数据文件

| 文件 | 内容 | 来源 | 可否自动更新 |
|---|---|---|---|
| `shared/data/loco_roster.csv` | 16622 行号段：`型号,起号,止号,配属单位,备注,制造厂` | LBJ_Console（GPL-3.0） | ✅ 可（§4） |
| `shared/data/loco_types.csv` | 176 行：`code,shortCode,name` | 解码器 `LOCO_TABLE` + LBJ_Console `loco_type_info.csv` | ❌ 协议常量，随版本走 |
| `shared/data/loco_specs.json` | 45 个车型的技术参数 | `desktop/cr_lbj/data/loco_info.py` 导出 | ❌ 随版本走 |
| `shared/data/places.csv` | 49 个预设中心坐标 | 本项目整理 | ❌ |

`loco_roster.csv` 与 `loco_types.csv` 都能用 `python tools/gen_shared_data.py` 重新生成/校验。

### 2.3 匹配规则（两端必须一致）

```python
model = short_code(code=locoCode) or short_code(name=型号文本)   # 归一成 DF4/SS4/HXD1D
number = int(数字部分)                                            # "0123" → 123
hit = first(row for row in roster[model] if row.start <= number <= row.end)
```

- 别名只有两条：**`DF4B→DF4`、`DF4R→DF4`**（号段表把东风 4B/4R 并进 DF4 统计）。
- **不做泛化前缀回退**：`HXD1D` 绝不能退成 `HXD1`（那是两种车、两个段）。
- 查不到号段 ≠ 车型不存在：返回值里 `ok`（认出型号）与 `exact`（号段命中）分开，
  界面因此能区分「配属未知（号段未收录）」和「型号未收录」。
- 号段表里有 3 行配属为空（上游即缺），显示成「原表未标注配属」，不猜。
- 型号未收录时给**开头相同**的候选（`suggest_models`，最多 4 个）作提示，不自动采用。

### 2.4 已知限制

- 号段表是**人工维护的静态快照**，新造机车/新配属会有滞后；界面上请显示数据更新日期。
- 号段可能重叠（同一型号多条区间都含该号），我们取第一条并在结果里带 `alternatives`，
  界面有歧义时可提示"另有 N 条候选"。
- 只覆盖**机车**（HXD/SS/DF/HXN/FXN 等）；动车组配属看在车次查询的 `carOwner`。

## 4. 数据自动更新

### 4.1 机制

```
内置快照 shared/data/loco_roster.csv（只读，随安装包）
        ↑ 回退
用户覆盖层 %LOCALAPPDATA%\CR-LBJ-Receiver\data\loco_roster.csv（可写，更新写这里）
        ↑ 优先读取
        └─ 更新源：GitCode API（GitHub 国内镜像）
           GET https://api.gitcode.com/api/v5/repos/CCCccc233/LBJ_Console/contents/loco_info.csv?ref=resources
           → JSON {content: base64(csv), sha: "..."}
```

读取顺序由 `desktop/cr_lbj/data/paths.py` 统一决定：`CRLBJ_DATA_DIR` → 用户目录 → exe 同级
`shared/data` → `_MEIPASS/shared/data` → 仓库 `shared/data`。
**所以更新只是往最外层写一个文件，内置快照永远在，随时可回退。**

### 4.2 更新流程

1. 读 `data_manifest.json` 里的 `lastCheck`，未超过间隔（默认 7 天）且非强制 → 跳过；
2. 拉上游 `sha` 与内容，**先与本地内容做归一化比对**（去行尾空白/末尾空行），一致则只记 sha；
3. 内容不同 → **严格校验**：
   - 行数 ≥ 15000；型号数 ≥ 120；配属单位中中文行 ≥ 50（防字段错位/HTML 错误页）；
   - 畸形行（字段不足、号段非数字、区间倒置）占比 ≤ 2%；
4. 校验不过 → **丢弃，保留旧文件**，返回失败原因；
5. 通过 → 原子写（`.tmp` → rename），旧文件留 `.bak`，更新 `data_manifest.json`
   （sha / 行数 / 型号数 / 抓取时间 / 来源 / 路径）；
6. `loco_roster.invalidate()` 让内存缓存失效，界面下次读取即新数据。

### 4.3 触发点

| 端 | 自动 | 手动 | 回退 |
|---|---|---|---|
| 桌面 | 启动后延迟 20s 后台检查（`dataAutoUpdate` 默认开，间隔 `dataUpdateIntervalDays` 默认 7 天，失败只记日志） | 工具 → 检查数据更新（机车配属表） | `updater.restore_backup()`（有 `.bak` 时） |
| 安卓 | 启动后后台检查（距上次 > 7 天），失败静默 | 设置 → 数据 → 立即检查更新 | 同上（留 `.bak`） |

### 4.4 相关配置项

| 键 | 含义 | 默认 |
|---|---|---|
| `dataAutoUpdate` | 是否自动检查更新 | `true` |
| `dataUpdateIntervalDays` | 自动检查间隔（天） | `7` |
| 环境变量 `CRLBJ_DATA_DIR` | 覆盖用户数据目录（便携/测试） | 空 |
| 环境变量 `CRLBJ_DATA_SOURCE_URL` | 换成自建镜像（返回同样的 JSON 结构） | 空 |

### 4.5 离线 / 内网行为

- 完全离线：自动检查失败 → 日志一行「检查更新失败：网络不可达」，界面照常用内置快照；
- 内网自建镜像：设置 `CRLBJ_DATA_SOURCE_URL` 指向自己的接口即可（结构见 4.1）；
- 上游改版导致 JSON 结构变化：会被 `返回结构不对` 拦住，不会写坏数据。

## 5. 与参考项目的差异（为什么没照抄）

| 参考 | 我们采用的 | 不采用的原因 |
|---|---|---|
| LBJ_Console（Flutter） | 号段匹配思路、界面分区方式 | 它的 `locoInfo` 调用把**车次号当车号**传（`G1` 解析必失败），配属几乎恒为空——这个坑不能抄 |
| LBJ_Console | 只借数据，不借逻辑 | 它用的是全称式配属（"上海铁路局集团有限公司 上海机务段"），号段表是简称式（"上局沪段"），混用会 100% 匹配不上；我们全库只用号段表原样文本 |
| RailGo | 直接接它公开接口 | 无 |
| rail.re | **未接入** | 接口存在性只有第三方客户端代码佐证，本环境无法验证响应结构；宁可先不接，也不写"看起来能用"的假实现 |
